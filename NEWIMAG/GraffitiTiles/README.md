# Re:Trap — 이어지는 그래피티 Wang 타일

Play 바닥 9장 + 벽 9장, Build 색상 변형 18장. 낙서와 콘크리트 면은 built-in image_gen 생성 결과다. 코드로 선·곡선·도형을 그리지 않았다. 코드 작업은 중앙 픽셀 샘플링, 팔레트 치환, 원본 조각 합성, 2px 경계 교체, 목업 배치와 비교 라벨뿐이다.

## 파일

- `_1x/Floor_L{0..2}_R{0..2}.png`: 32×32, 9장.
- `_1x/Wall_T{0..2}_B{0..2}.png`: 32×32, 9장.
- `_1x/Build/`: 동일 이름과 픽셀 배치의 청회색 변형 18장.
- `Sheet_Floor_6x.png`, `Sheet_Wall_6x.png`: 행=입구 종류, 열=출구 종류. 각 타일을 최근접 6배 확대하고 출력상 2px 간격으로 배치한 580×580 시트.
- **`Strip_3x.png`**: 24칸×3줄, y=0,7,19, 2304×336. 줄 간격은 원본 8px. 양 끝 경계는 0.
- `Strip_Build_3x.png`: 같은 배치의 Build 확인용 띠.
- `Strip_Wall_3x.png`: 세로 24칸×3열, x=0,7,19, 336×2304. 위·아래 바깥 경계는 0.
- `Mock_3x.png`: 640×360 화면을 최근접 3배 확대한 1920×1080.
- `Compare_3x.png`: 이전 A 목업 / 새 목업을 원래 크기로 위아래 합성, 한국어 라벨 포함. 1920×2256.
- `Edges/`: 실제 2px 표준 단면 PNG 6개와 모든 좌표의 정확한 색을 적은 `profiles.txt`.
- `Sources/`: 채택한 image_gen 원본 2개와 모든 시도의 프롬프트 `prompts.md`.
- `validation.txt`, `sampling.txt`, `strip_sequence.txt`: 검사 결과, 샘플 등록 보정, 띠 타일 조합.
- `assemble.cs`, `rebuild.ps1`: 결과 재구성 코드. 저장소 루트에서 `powershell -NoProfile -File NEWIMAG/GraffitiTiles/rebuild.ps1` 실행.

## 가장자리 단면

좌표는 0부터. Floor는 위→아래 행 y, Wall은 왼쪽→오른쪽 열 x. 같은 단면을 양쪽에 복사하며, 추출한 한 픽셀 열/행을 두 번 복사해 2px 폭을 만든다. 따라서 맞닿는 최외곽 픽셀뿐 아니라 경계 2px 전체도 같다. 바탕 콘크리트 색까지 포함한 정확한 32개 색 배열은 `Edges/profiles.txt`가 정의한다.

| 종류 | Floor 단면 | Wall 단면 |
|---|---|---|
| 0 | 낙서 없음. Floor00의 x=2 열 추출 | 낙서 없음. Wall00의 y=2 행 추출 |
| 1 | Floor11 x=2: y=14 `#92223F`, y=15–16 `#B83450` | Wall11 y=2: x=15–16 `#B83450` |
| 2 | Floor22 x=2: y=20 `#E7D8CE`, y=19 회색 가장자리 `#9CA7AC` | Wall22 y=2: x=23 `#F7EEE4` |

Floor 윗면 y=0..2는 A안 `Tile_Play_Floor.png`에서 잘라 모든 타일에 같은 위치로 복사한 뒤 허용 팔레트로 정리했다. 경계의 윗면 단면은 세 종류 모두 동일: y=0 `#F7EEE4`, y=1..2 `#E7D8CE`. 이 밝은 윗면은 0번 경계에서도 유지하며 낙서로 세지 않는다. 흰색 선의 흘러내림은 타일 내부에 있다.

Build는 전체 픽셀 좌표를 보존하는 결정적 청회색 팔레트 치환이다. 새로운 낙서를 생성하지 않았으며, 경계도 같은 치환이 적용된다.

## 결정적 배치 및 실제 맵

해시는 unsigned 32bit, 곱셈 overflow wrap, 오른쪽 시프트는 logical shift:

```text
h = uint32(x*73856093) XOR uint32(y*19349663)
h = h XOR (h >> 13)
h = uint32(h * 0x5bd1e995)
h = h XOR (h >> 15)
kind = h % 3
```

Floor: E(x,y)는 (x,y)와 (x+1,y)의 지형 종류가 같고 둘 다 솔리드일 때만 kind, 아니면 0. L=E(x−1,y), R=E(x,y).

Wall: V(x,y)는 (x,y)와 (x,y+1)의 종류가 같을 때만 kind, 아니면 0. JSON 원점이 왼쪽 아래이므로 **T=V(x,y), B=V(x,y−1)**. 이미지 행 좌표와 월드 y 방향을 혼동하지 않는다.

목업은 `Assets/StreamingAssets/Maps/stage_01.json`을 파싱했다. 25×14, grid[y*25+x], 왼쪽 아래 원점. grid 1=Floor, 2=Wall, 3=Ceiling; Ceiling은 별도 타일 요청이 없어 Floor 시각을 재사용한다(현재 스폰 화면 밖). 네 trapSlots는 anchor에 따라 Floor/Wall 솔리드로 덮어써서 중간 발판 x=10,y=3도 연결된다.

카메라는 월드 픽셀 x=[0,640), y=[0,360)이며 화면 y=360−월드 y. 전체 800×448 맵의 스폰 주변을 잘랐다. 스폰 (2,1), 바닥 y=0. Hero_Idle.png의 첫 96×96 프레임을 그대로 사용하고, 알파가 있는 최하단 발을 바닥 윗면에 정렬했다. 배경은 `#19181F` 단색. 맵 파일·게임 코드는 변경하지 않았다.

## 시도와 검사

- Floor image_gen **3회**, 3번째 채택. 이전 시도는 입출구 방향과 높이 오류가 있었다.
- Wall image_gen **2회**, 2번째 채택. 첫 시도는 0번 위쪽 가장자리에도 흰색 선이 닿았다.
- Wall01은 생성된 하단 빨간 포트가 오른쪽으로 치우쳐 전체 타일 조각을 3px 왼쪽 이동해 붙였다. 비는 오른쪽 3px은 같은 타일의 왼쪽 콘크리트 조각을 복사했다.
- Floor22는 원본의 미세 격자 등록 오차로 가는 선에 한 픽셀 공백이 생겨, 원본 샘플 중심을 x+1,y−1 **원본 픽셀** 이동했다. 그린 픽셀은 없고, 기존 2px 경계와 윗면은 유지했다.
- 각 세트에서 가능한 같은 종류 접합 27쌍 × 32 × 2 = **1,728/1,728 RGBA 픽셀 일치, 100%**. Play Floor/Wall 및 Build Floor/Wall 모두 통과, 총 **6,912/6,912**.
- Play의 양쪽 비영(1·2) 포트 조합 4개씩, 총 8개 모두 페인트의 8방향 연결 경로를 확인했다. Floor y<4 윗면은 검사에서 제외했다.
- 36장 전부 32×32, 알파 255. 최대 16색. 팔레트는 지정한 두 파일의 합집합 안에서만 선택했다.

## 한계

- image_gen이 요청한 정확한 8배 픽셀 블록/768 해상도를 지키지 않고 1254×1254 및 더 미세한 질감을 반환했다. 이를 3×3 셀로 나눠 32×32 중앙 샘플링했다. 최종 타일과 확대 출력은 정확한 픽셀 격자이지만 원본의 작은 스프레이 점 일부는 사라졌다.
- 생성된 포트에서 추출한 최종 단면은 위 표의 좌표·두께다. 프롬프트의 잠정 좌표와 다르므로 게임 구현은 이 최종 정의를 사용해야 한다.
- 픽셀 경계 일치와 페인트 연결 경로는 보장하지만, 곡선의 기울기와 콘크리트 균열 방향까지 모든 조합에서 매끄럽게 이어지는 것은 아니다. A안의 윗면 픽셀은 재사용했지만 콘크리트 본체는 해당 스타일을 따른 새 생성 질감이다.
- 9개 조합이므로 같은 조합은 같은 그림을 재사용한다. 0번 경계에서는 의도적으로 낙서가 끝난다. 서로 다른 지형 종류나 Floor↔Wall 모서리에는 회전 연결 타일이 없다.
- Build는 별도 아트 디렉션을 거친 생성본이 아닌 낮은 대비의 색상 변형이다. 게임 내 임포트·필터 설정 및 런타임 적용은 하지 않았다.

모든 프로젝트 출력은 이 폴더 안에만 있다. git을 사용하지 않았다. 별도 임시 파일은 남기지 않았다.
